% ============================================================
\section{Model Compatibility, Parameter Governance, and Digital-Twin Readiness}
\label{sec:io_governance_digital_twin}
% ============================================================

The \texttt{Data IO} subsystem is now more than a file importer/exporter.  The
current implementation treats I/O as a standards-aware model contract: each
rich component type declares how it is preserved in native JSON, projected to
the canonical model, exported to GridLAB-D and OpenDSS, checked against
standard-aware parameter rules, and scored for digital-twin readiness.

\subsection{Component Compatibility Contract}

For each registered component collection \(c\), the registry stores a policy
tuple
\[
  \Pi_c =
  \left(
    \pi^{\mathrm{json}}_c,
    \pi^{\mathrm{can}}_c,
    \pi^{\mathrm{gld}}_c,
    \pi^{\mathrm{dss}}_c,
    \nu_c
  \right),
\]
where \(\pi\) is one of \texttt{Exact}, \texttt{Equivalent},
\texttt{Aggregated}, \texttt{BoundaryInjection}, \texttt{Projected},
\texttt{InternalOnly}, \texttt{Unsupported}, or \texttt{DiagnosticOnly}, and
\(\nu_c\) is the numerical verification scope.  This makes the information
loss explicit.  For example, a \texttt{Load} can be exact in JSON and exact in
OpenDSS/GridLAB-D static exchange, whereas a VSC converter is native/canonical
inside \texttt{hacdcpf} and only a boundary injection in GridLAB-D static
snapshots.

\begin{longtable}{L{0.24\linewidth}L{0.24\linewidth}L{0.42\linewidth}}
\toprule
Policy & Interpretation & Typical use \\
\midrule
\endhead
\texttt{Exact} & All fields required by the target semantic model are preserved. & Native JSON and canonical rows for first-class components. \\
\texttt{Equivalent} & The target has an equivalent object but not every native field is preserved. & Transformer, source, and phase-domain reductions. \\
\texttt{Aggregated} & Several native records are folded into one target object. & Charging stations, flexible loads, and balanced views. \\
\texttt{BoundaryInjection} & The network only sees a solved or scheduled terminal injection. & DER/VPP/microgrid/VSC external snapshots. \\
\texttt{Projected} & The rich model is transformed into a lower-dimensional native model. & Rich-to-canonical projection for transformers and switches. \\
\texttt{InternalOnly} & The component is executable only in the native hybrid model. & DC buses, DC branches, and DC/DC converters for AC-only external tools. \\
\texttt{Unsupported} & No target representation is currently declared. & Unsupported external-format objects. \\
\texttt{DiagnosticOnly} & The target format has a related control object, but export/import is not an executable contract yet. & Regulator-control diagnostics before sequence replay is implemented. \\
\bottomrule
\end{longtable}

\subsection{Parameter Governance Model}

Each rule \(r\) in the parameter catalog is a tuple
\[
  r =
  \left(
    \mathrm{type}, \mathrm{path}, \mathrm{parameter}, \mathrm{category},
    [\ell,u], \mathrm{required}, \mathrm{standard}, \mathrm{units},
    s_{\mathrm{missing}}, s_{\mathrm{range}}
  \right).
\]
The categories are \texttt{Static}, \texttt{Dynamic}, \texttt{Transient},
\texttt{Failure}, and \texttt{Reliability}.  The audit evaluates each available
value \(x\) with the configured inclusivity flags:
\[
  \mathrm{violate}(x;r) =
  [x < \ell] \lor [x > u] \lor [x \notin \mathbb{R}],
\]
with the strict inequalities adjusted when either bound is open.  Missing
required fields produce the rule's \texttt{missing\_severity}; range violations
produce \texttt{range\_severity}.  Additional consistency checks such as
\(\mathrm{soc}_{\min}\le \mathrm{soc}_{0}\le \mathrm{soc}_{\max}\), tap-order
checks, and ZIP percentage-sum checks are emitted through the same finding
structure.

\paragraph{Implemented rule families.}
The current catalog contains hundreds of rules and covers:
\begin{itemize}
  \item CIM-style asset, topology, base-voltage, impedance, transformer, and
        operational-limit fields;
  \item IEC~60909 source, motor, and short-circuit feasibility fields;
  \item IEEE/IEEE~421.5 synchronous-machine, governor, exciter, inertia, and
        transient reactance placeholders;
  \item IEEE~1547 and NERC inverter-based resource, DER, BESS, PV, wind, and
        plant-controller profile readiness;
  \item GridLAB-D/OpenDSS ZIP and phase-domain load fields;
  \item reliability metadata such as failure rate, forced-outage rate,
        MTTR/MTBF, and scheduled outage time.
\end{itemize}

\subsection{Dynamic Model Profile Preservation}

The parameter audit treats \texttt{DynamicModelProfile} as the native contract
for transient and dynamic compatibility.  It checks the presence of
\texttt{standard}, \texttt{model\_name}, \texttt{parameter\_set},
\texttt{source\_id}, nested control blocks, and common dynamic parameter keys
such as \texttt{H}, \texttt{D}, \texttt{Xd}, \texttt{Td0p}, \texttt{droop},
\texttt{pll\_kp}, and \texttt{pll\_ki}.  The projection layer preserves dynamic
profiles through rich-to-canonical transformations for DER aggregations and
energy-router expansions, so the transient layer can still recover the
provenance of a projected equivalent.

\subsection{Digital-Twin Readiness Score}

The digital-twin report is a weighted score over eleven criteria.  Let
\(\rho_k\in[0,1]\) be the criterion readiness ratio and \(w_k\) its configured
weight.  The implementation reports
\[
  S = \sum_k w_k\rho_k,\qquad
  S_{\max} = \sum_k w_k,\qquad
  R = S/S_{\max}.
\]
The maturity level is derived from \(R\):

\begin{longtable}{L{0.16\linewidth}L{0.28\linewidth}L{0.46\linewidth}}
\toprule
Level & Label & Interpretation \\
\midrule
\endhead
L0 & file exchange & Files may parse, but no executable model contract is established. \\
L1 & static network model & Asset identity and basic topology are present. \\
L2 & executable simulation model & Static executable data are mostly present and range-gated. \\
L3 & validated model & Numerical verification and external-format scopes are declared. \\
L4 & synchronized operational twin & Telemetry/state/event/reliability surfaces are substantially ready. \\
L5 & predictive closed-loop twin & Provenance, validation, uncertainty, replay, and control loops are mature. \\
\bottomrule
\end{longtable}

\subsection{Implemented Readiness Criteria}

\begin{longtable}{L{0.18\linewidth}L{0.22\linewidth}L{0.50\linewidth}}
\toprule
Criterion & Dimension & Evidence currently used \\
\midrule
\endhead
\texttt{DT-IDENTITY-01} & Asset identity & Ratio of populated components with stable names. \\
\texttt{DT-TOPOLOGY-01} & Topology connectivity & Presence of bus objects and branch/transformer/converter edge objects. \\
\texttt{DT-PARAM-01} & Electrical parameters & Parameter audit hard errors and warnings normalized by checked parameters. \\
\texttt{DT-DYNAMIC-01} & Dynamic behavior & Ratio of transient-capable devices carrying nonempty \texttt{DynamicModelProfile}. \\
\texttt{DT-TELEM-01} & Telemetry observability & Ratio of components with name/customer/location-style telemetry anchors. \\
\texttt{DT-STATE-01} & State synchronization & Ratio of components with voltage, dispatch, SOC, status, or control seeds. \\
\texttt{DT-EVENT-01} & Scenario events & Ratio of components exposing controllable or event-capable surfaces. \\
\texttt{DT-RELIABILITY-01} & Reliability lifecycle & Ratio of reliability-capable components with failure/repair metadata. \\
\texttt{DT-IO-01} & Standards interoperability & Weighted JSON/canonical/GridLAB-D/OpenDSS representation coverage. \\
\texttt{DT-VALID-01} & Numerical validation & Populated component classes with native or external verification scopes. \\
\texttt{DT-GOV-01} & Provenance governance & Dynamic provenance plus availability of parameter and readiness registries. \\
\bottomrule
\end{longtable}

\subsection{GUI Workflow}

The GUI exposes this analysis through the unified \texttt{Data IO} report.  The
same endpoint can be launched from transient-model compatibility checks, but
the results are intentionally routed back to the IO dashboard so that users do
not have to inspect separate screens for import/export coverage, standard
profiles, parameter health, and digital-twin maturity.  The dashboard currently
shows:
\begin{itemize}
  \item component instance coverage and GridLAB-D/OpenDSS representation ratios;
  \item parameter health counts by severity and category;
  \item a digital-twin maturity gauge and dimension bar chart;
  \item detailed readiness findings with criterion ID, evidence, standard
        basis, severity, and improvement direction;
  \item the standards-profile registry and parameter-rule catalog.
\end{itemize}

\subsection{Review and Regression Hooks}

The focused regression file \texttt{tests/test\_component\_io\_mapping.cpp}
checks registry coverage, rich JSON round-trip preservation, dynamic profile
projection, parameter-rule category coverage, invalid-parameter findings, and
digital-twin readiness behavior.  The API smoke path is:
\begin{verbatim}
./build/macos-release/run_gui_server --port 8097
curl -X POST http://127.0.0.1:8097/api/session/load_builtin \
  -H 'Content-Type: application/json' \
  -d '{"case":"ieee24_3area_acdc_expanded"}'
curl http://127.0.0.1:8097/api/io/model_compatibility
\end{verbatim}

For the built-in IEEE~24 hybrid case, the report currently exposes the intended
gap: many static parameters and external-format mappings are available, while
dynamic profiles and provenance are still sparse.  This is why the report is
useful for future digital-twin work: it distinguishes ``model parsed'' from
``model is dynamically, operationally, and externally validated.''
