\section{Implementation Gap and Stub Audit}
\label{sec:implementation_gap_audit}
% ============================================================

This chapter records a code-backed audit of implementation gaps, placeholder
paths, and documentation statements that can overstate the current runtime
capability.  It is intentionally separated from the mathematical model chapters:
a formula in this notebook is not proof that the corresponding production code
solves that model end-to-end.

\subsection{Audit Method}

The audit covered \texttt{src/}, \texttt{include/}, \texttt{tests/}, and
\texttt{docs/technical\_notebook/sections/}.  The review combined direct source
inspection with searches for high-signal markers such as \texttt{TODO},
\texttt{stub}, \texttt{not\_implemented}, \texttt{unimplemented},
\texttt{placeholder}, \texttt{dummy}, \texttt{simplified}, \texttt{approximate},
\texttt{fallback}, and \texttt{unsupported}.  The raw marker counts are not, by
themselves, a defect count: many \texttt{fallback} and \texttt{unsupported}
occurrences are legitimate guardrails.  The findings below list only cases where
the public API, tests, or documentation can mislead a user about implemented
behavior.

\subsection{Documentation Mismatches Found}

Several existing notebook statements should be treated as stale or too broad:

\begin{itemize}
  \item \texttt{sections/17\_three\_stage\_reliability.tex} says the current C++ file is a stub returning a graceful error.  The source now implements a Julia bridge instead.  The correct boundary is: no native C++ MILP is present; external Julia/Gurobi execution is required.
  \item Broad ``fully implemented'' wording in \texttt{sections/00\_scope.tex}, \texttt{sections/02\_component\_models.tex}, and \texttt{sections/02c\_output\_field\_dictionaries.tex} was too strong because FMEA options and the resilience MIP entry point have explicit unimplemented/stub behavior.  Those statements should remain narrowed to documented runtime boundaries.
  \item \texttt{sections/14\_test\_results.tex} correctly records that some stub tests pass, but those passing tests should not be used as evidence that the underlying algorithm exists.
\end{itemize}

\subsection{Recommended Acceptance Criteria}

Before presenting the module as complete, the following checks should be added
or tightened:

\begin{enumerate}
  \item Replace \texttt{solve\_distribution\_power\_flow} with a real radial or weakly meshed distribution solver, or remove/rename the public API so callers cannot mistake it for production functionality.
  \item Convert the distribution-PF stub tests into algorithmic tests on voltage drops, branch flows, losses, and non-convergence behavior.
  \item Either implement the six FMEA options or default them to \texttt{false} and return an explicit unsupported-feature error when a caller enables them.
  \item Rename the resilience MIP entry point or implement a true multi-period MIP.  A test should verify that the MIP path uses a different formulation from the heuristic path.
  \item For three-stage reliability, add an integration smoke test that distinguishes missing Julia/Gurobi environment, malformed JSON, and successful external solve.  The notebook should state that the MILP engine is external, not native C++.
  \item For network reconfiguration, expose the skipped B\&C fallback as an option or status code so ``heuristic failed'' is not confused with mathematical infeasibility.
  \item Implement DC OPF dual extraction and add LMP regression tests, or mark \texttt{lmp} fields as unavailable instead of zero-valued economics.
  \item Add JPC JSON round-trip tests with non-empty rich components, especially flexible/asymmetric loads, three-phase branches, PV, storage, energy routers, high-voltage circuit breakers, and microgrids.
\end{enumerate}

\subsection{Audit Conclusion}

The repository is not an empty shell: many PF, OPF, graph, I/O, resilience, and
reliability components are implemented and tested.  However, several public
surfaces are materially weaker than a reader of the technical notebook could
assume.  The most serious issues are the distribution-PF stub, the FMEA option
contract mismatch, the resilience MIP alias to a heuristic, the skipped
reconfiguration MILP fallback, and stale three-stage reliability documentation.
Those items should be treated as release blockers if the project is being sold
as a complete hybrid AC/DC distribution-system simulation studio.
