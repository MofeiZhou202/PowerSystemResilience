# Windows LP 分解计时与 INTEL/2、INTEL/4 重复稳定性

## 实验范围与复现身份

2026-09-11 在 Windows 11 10.0.26200、Intel Core i9-12900H（14核/20逻辑处理器）、约32GB内存上完成。本轮聚焦 LP 分解计时和线程选择，不实施新的数值算法、LTCG、PGO 或 AVX2 优化。全程使用本地源码、依赖和数据，不执行网络访问。电源计划维持 Balanced，不设置 CPU affinity。

- 分支：`release/windows-self-contained`。
- HEAD：`75c6e1922839d4775c27eacda833df386e95f476` **加未提交工作区修复**；`origin/main=b42a0540` 不是本轮构建基点，不能直接用 main 的数字替代。
- 编译：Visual Studio 2022 / MSVC 19.44，Ninja Multi-Config，Release x64；核心 `/O2 /Ob2 /Oi /fp:fast /MD`。
- CMake：`MIPSOLVERS_MKL_THREADING=INTEL`，`MIPSOLVERS_USE_OPENMP=ON`，`MIPSOLVERS_ENABLE_IPO=OFF`，`MIPSOLVERS_ENABLE_NATIVE_ARCH=OFF`，`MIPSOLVERS_PGO_MODE=OFF`。
- oneMKL 2026.0.1、LP64，本地 `third_party/oneapi-mkl`；静态线程层及随程序部署的 `libiomp5md.dll`。无需系统 oneAPI 路径。
- 环境：`OMP_NUM_THREADS=1`，`MKL_NUM_THREADS=2` 或 `4`，`MKL_DYNAMIC=FALSE`，`MKL_CBWR` 未设置；每个 LP 进程检查实际 `mkl_max_threads`。
- NETLIB 二进制 SHA256：`cdcd2dbe23cf175a7859048d110cd4028eb1c4213bc17a9fe0374eafe2bac28e`。

## 测量协议

```powershell
python tools/windows_lp_stability.py --stage overhead --output reports/windows_stability_20260911
python tools/windows_lp_stability.py --stage stability --output reports/windows_stability_20260911
python tools/windows_lp_stability.py --stage gates --output reports/windows_stability_20260911
```

以上阶段顺序执行。不得同时构建或运行其他求解任务，多个构建目录共享 `tests/Release` 输出。复测需另取输出目录。

稳定性阶段：每档先运行单独预热进程，再进行20个区组；奇数组2/4、偶数组4/2。每进程求解 dfl001、greenbea、maros-r7，`native-ipm-direct --repeat 1 --time-limit 15 --max-iterations 100000`，计时开启。每案例每档20个样本。新进程仍包含首次库调用，不能称为完全热态。

准确性要求成功状态且原模型目标相对误差≤1e-5、归一化原始违反≤1e-7。稳定性优先：4线程各例P95≤2线程的1.1倍，且区组三例合计中位数至少降低5%，才进入4线程推荐候选；另需全集、NLP和CTest验收。P95用nearest-rank，即20样本中的第19个值。

## 分解计时揭示的成本

新增 `MIPSOLVERS_LP_FACTOR_TIMING=1`，默认关闭。每个LP变体输出一行 `LP-FACTOR` JSON，失败变体也保留。装配/符号分析/数值分解为互斥区间，嵌套子项从父项扣除；加 `other_ms` 后等于 `variant_ms`。后端API中的格式准备计入相应API，不等于MKL内部纯计算时间。`retry_ms`是正则化重分解的重叠子集，不能再加到总时间上；外层变体重跑及自适应后端试算不计为该重试次数。

下表为20次的**算术平均**，每次先合并同案例所有变体；使用平均值便于分类加和。单位ms，舍入会产生末位误差。

| 案例 | 线程 | 装配 | 符号分析 | 数值分解 | 其他 | 正则化重试子集 |
|---|---:|---:|---:|---:|---:|---:|
| dfl001 | 2 | 24.71 | 439.93 | 2440.40 | 447.83 | 0 |
| dfl001 | 4 | 24.69 | 434.62 | 1408.84 | 365.74 | 0 |
| greenbea | 2 | 55.80 | 200.24 | 1136.83 | 1712.10 | 225.10 |
| greenbea | 4 | 57.79 | 204.25 | 1020.37 | 1682.34 | 197.62 |
| maros-r7 | 2 | 197.45 | 174.75 | 508.83 | 216.51 | 0 |
| maros-r7 | 4 | 201.30 | 177.01 | 357.42 | 200.83 | 0 |

- **dfl001**：每次1变体、44迭代、45次数值分解、5次符号分析，无正则化重试。2线程数值分解占72.79%，4线程降至63.07%；分解中位数2426.32→1402.82ms，是本轮最明确的并行收益来源。后续可研究已分析模式复用，但需先证明结构/置换合同，不直接删除分析。
- **greenbea**：每次2变体，2线程总分解297–670次、正则化重试79次；4线程292–551次、正则化重试65次。返回结果的迭代数范围46–419/43–302，**不是所有变体累计迭代数**。运行时间主要受求解轨迹影响；应先细分失败变体、回代/残差及恢复过程，再形成减少重试或更换方程的理论方案。当前不能宣称非确定性已解决。
- **maros-r7**：每次1变体、21迭代、22次数值分解、4次符号分析，无正则化重试。4线程下装配与符号分析合计占约40.4%，继续增加分解线程的收益受到串行工作限制。后续优先研究结构复用及装配访存。

本次只增加诊断，不实施上述后续数值优化。计时口径和字段见 [手册9.7](../manual/09-testing-benchmarks.md#97-lp-分解计时与-intel-线程稳定性协议)。

## 预测与实测、尚未解决的问题

| 预先预测 | 实测 | 解释 |
|---|---|---|
| 4对2线程合计降5–15% | 区组中位数降18.50% | 超出区间，已按保守口径触发R6偏差复核：低估dfl001分解并行占比，greenbea工作量也不固定 |
| 开启计时开销<2% | 2/4线程三对观测差异中位数+0.609%/+1.338% | 数值轨迹有噪声，不能据此证明纯探针开销<2% |
| 同线程开关计时的目标/残差/迭代一致 | 不成立 | 同样关闭计时的重复运行本身也不同；准确门槛通过不代表逐位复现 |
| 三长尾各减半→原基线全集降31.54% | 本次未验证此条件 | 保持条件预测；不能把本轮2/4线程比较称为实现31.54% |

4线程开关计时三对差异−5.687%、+3.362%、+1.338%，2线程+0.162%、+1.105%、+0.609%；共42次（含预热）均准确。负差异不是计时探针加速算法的证据。

对非确定性按实现→机器→假设→理论顺序复核：scope不写数值矩阵；线程归约/调度可能影响舍入，既有PARDISO自适应选择也包含耗时比较；当前记录不足以唯一归因。固定后端或CBWR实验应独立进行，不能在2/4比较中途改变。当前 `/fp:fast` 也未做独立对照。LTCG/PGO/AVX2开关虽可用，尚无本轮验收证据，推荐配置继续关闭。

## 全集与 NLP 准确性验收

计时关闭，同一二进制，每档 NETLIB 90例×3次×2求解器，均 **540/540准确**，两档合计 **1080/1080**。目标相对误差最大约1.250e-6，归一化原始违反最大9.959e-8。未观察到失败或超时。

| 求解器 | INTEL/2 准确数 | INTEL/4 准确数 | 2线程270次总耗时 ms | 4线程270次总耗时 ms | 4线程降时 |
|---|---:|---:|---:|---:|---:|
| Native-IPM direct | 270/270 | 270/270 | 37063.89 | 35386.44 | 4.53% |
| Native-Auto | 270/270 | 270/270 | 35532.78 | 39243.92 | −10.44% |

两求解器混合总耗时72596.67→74630.36ms，反而增加2.80%。若使用“各案例中位数之和”口径，IPM为12185.44→12028.65ms（降1.29%），Auto为11464.96→11260.16ms（降1.79%）。这说明总耗时对少数慢重复很敏感；必须同时公开这些口径，不能只选有利数字。

全集阶段每档只有一个进程，包含每例3次重复，且先2后4；它是准确性验收及辅助耗时观测，不替代长尾20组交替进程的P95实验。尤其Auto未做20组稳定性测试，不能据此宣称4线程全面更快。准确性通过也不意味着没有接近容差边界的结果。

HS071每档 `nlp_open_benchmark.exe 5 1e-7`：原生禁用fallback，5/5准确、15迭代、绝对目标误差5.823e-8；Ipopt 5/5准确、8迭代、误差1.815e-8。两档合计20/20准确。求解容差1e-7，验收目标绝对误差/原始违反仍为1e-6，未放宽门槛；旧1e-6求解容差的原生结果误差1.006e-6，仍保留为失败记录，不与本次作等条件速度比较。

## Windows 配置建议的适用范围

按预先固定的20组性能规则，**本机 LP direct 推荐 INTEL/4**：三例中位数及P95门、全集/NLP准确性和最终CTest全部通过。**Auto或混合任务不统一升级为4线程**，保留2线程作为资源更保守的运行选项；其多进程尾延迟和任务吞吐需独立实验。该建议不修改仓库全局默认，也不把当前硬件结果外推到所有Windows机器。

使用上述已验收构建，在启动求解进程前设置：

```powershell
$env:OMP_NUM_THREADS='1'
$env:MKL_NUM_THREADS='4'
$env:MKL_DYNAMIC='FALSE'
$env:MIPSOLVERS_LP_FACTOR_TIMING='0'
```

Auto或多个求解任务并发时先使用 `MKL_NUM_THREADS=2`，再按实际任务预算复测；本轮未测试多个进程同时求解的吞吐。保持电源计划、编译开关及CBWR与实验一致；诊断时才开启LP计时。没有证据支持此时同时开启LTCG、PGO或AVX2来宣称额外收益。
